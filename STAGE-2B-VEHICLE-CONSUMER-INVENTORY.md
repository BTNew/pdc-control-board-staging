## Authority definitions

- **Canonical shared master:** `public.vehicles` plus `public.vehicle_aliases`; raw evidence is held separately in `vehicle_master_source_records`.
- **Sanitized contract:** `public.get_vehicle_core_snapshot()` from migration `028`. It returns an allowlisted core vehicle projection and master revision; it deliberately excludes `source_payload`, raw source evidence, deletion reason/timestamps, workflow state, QC/RFT actor fields, workshop state, and audit/history.
- **Legacy browser authority:** `window.VEHICLE_TRACKING_DATA.vehicles` merged with browser-local additions, edits and deletions by `app.js::buildVehicleData()`. It remains authoritative for the current main board until an approved reconciliation/cutover stage.
- **Direct read:** a query/PostgREST call touches `vehicles` rather than consuming an allowlisted RPC result.

## Import and reconciliation consumers

- **Navision/CSV:** `app.js` paste/text/file parser and confirmation paths consume stock, batch/order, VIN/frame and legacy local ID, then write `ADDED_KEY`, `EDITS_KEY`, tombstones and an import summary. Current result is browser-local and includes first-match `.find()` paths that must not be reused. Stage C3 maps one synthetic record at a time to 029 preview/apply; no bulk real import yet.
- **PD/job-card/work-file:** creates placeholder `PD-*` local records and writes added/edit/PO task/file state. A `PD-*` value is never a strong identity; only mapped core fields may reach a future preview and operational work stays separate.
- **Purchase orders:** reads stock/reference/VIN and may create a local PO vehicle plus edits/tasks/files/audit. PO reference is source-scoped evidence, not a global identity; no PO/work payload belongs in the core RPC.
- **Manual add, activation and detail edit:** current browser handlers can create `NEW-*` placeholders or apply mixed core/operational local patches. A future shared path must split strict core allowlisted edits from lifecycle/visibility/station/Parts/workshop data, reject placeholder-only identity and carry the expected canonical version.
- **Reviewed email vehicle import and AI file assistant:** current review flows write local vehicle/review drafts only. They remain deferred and must not call 029 automatically.
- **Autocare:** local scan/dispatch state only; never treat dispatch output as canonical vehicle identity.
- **Email/AI:** intake and parsing are untrusted review proposals. No automatic shared-master write is allowed.
- **Workshop legacy:** extract/validate/import tooling reads identity references and writes workshop bookings only; it must use canonical normalization/candidate semantics before any approved run.

## Cross-domain integrity and retention findings

These are inventory findings, not work authorized for migration 029:

- `vehicles.version` is shared by core and operational mutations. Because the 028 core audit JSON includes `version`, workflow/QC/RFT-only version bumps can create master-history rows at an unchanged master revision. A later design must either separate the master version or make history semantics explicit before consumer cutover.
- Many older child relationships still use `ON DELETE CASCADE`, including aliases, movements/work items, workshop bookings and downstream assignment/history, ETA/timeline/summaries, notifications and deleted snapshots. No hard-delete capability should be added until retention policy is reviewed.
- `vehicles.active_workshop_booking_id` has an FK to a booking but no database constraint proving that booking belongs to the same vehicle. Add a cross-row health check before relying on this pointer as authority.
- The IMAP bridge and email publisher contain anon-key fallback paths despite service-role error text. Existing RLS should make them fail, but a later ingestion-security change should remove the fallback and fail closed. This is not part of the Stage 2B vehicle cutover.
- Backup format remains `1`; concrete-payload compatibility is verified, but restore does not reject unknown `backup_format_version` values. Any future format bump must explicitly accept retained v1 payloads and reject unsupported versions.
- Current restore verification proves counts, FKs and selected relationships, but does not yet semantically cross-check alias ownership, source-evidence/history linkage or master-revision consistency beyond their constraints and row counts.

## Inventory conclusions

1. The only active direct frontend `vehicles` read found is `app.js::vehicleLifecycleSharedRef`; it uses `limit=1` and is the first mandatory cutover target.
2. `get_workshop_snapshot` and vehicle-intelligence snapshots are purpose-built vehicle-derived contracts and must not be replaced blindly by the core snapshot.
3. `scripts/workshop_legacy_import.py::fetch_reference_data` is the active non-test direct backend vehicle read; backup/restore and staging tests are privileged direct consumers by design.
4. The main board remains browser-local and consumes substantially more operational data than the sanitized core contract. Its cutover is deliberately later.
5. Broad authenticated `SELECT` on `vehicles` and `vehicle_aliases` cannot be retired until the lifecycle resolver, any script/reference lookup, and all undiscovered external PostgREST clients are proven migrated; database statement/log review is part of that proof.
6. No current email/AI path may call 029 apply automatically. Email and attachments remain untrusted proposals requiring human review.
